## 1. Pi SDK 到底接收什么

Pi 的模型调用层不是直接让上层拼 OpenAI / Anthropic / Gemini 各家的原生 HTTP JSON，而是先接收统一语义对象：

```ts
streamSimple(model, context, options)
```

其中最重要的是：

```ts
context = {
  systemPrompt,
  messages,
  tools,
}
```

理解：

```text
Agent 世界
Model + Context + Options
        ↓
pi-ai Provider Adapter
        ↓
OpenAI / Anthropic / Gemini 各自协议
```

所以 Pi SDK 输入层是统一的“模型语义格式”，Provider Adapter 再负责降级成具体厂商协议。

输出也不是单纯 `Promise<string>`，而是结构化事件流，例如：

```text
start
text_start
text_delta*
text_end
toolcall_start
toolcall_delta*
toolcall_end
done
```

这使前端可以直接按事件类型渲染，而不必把所有东西先拼成 Markdown。

# 2. ToolCall 从 LLM 到真正执行的完整流水线

今天最重要的一条主线：

```text
LLM ToolCall
    ↓
① Tool Registry：这个工具存在吗？
    ↓
② prepareArguments：模型参数能不能修正？
    ↓
③ validateToolArguments：是否符合 Schema？
    ↓
④ beforeToolCall：产品策略允许执行吗？
    ↓
⑤ tool.execute：真正执行
    ↓
⑥ catch：把运行时异常翻译成 Agent 可理解的数据
    ↓
⑦ afterToolCall：结果过滤 / 脱敏 / 修改
    ↓
ToolResultMessage
    ↓
下一次 LLM Turn
```

一句话记忆：

> Registry 决定“有没有这个能力”，Schema 决定“调用是否合法”，before hook 决定“允不允许做”，execute 决定“怎么做”，catch 把失败变成 Agent 可恢复的数据，after hook 决定“什么结果允许进入上下文”。

## 3. 第一道：根据 ToolCall.name 查 Tool Registry

LLM 只返回类似：

```ts
{
  id: "call_123",
  name: "bash",
  arguments: {
    command: "npm test"
  }
}
```

Agent Runtime 需要用名字在当前工具集合里找到真正实现：

```ts
const tool = tools?.find(
  (t) => t.name === toolCall.name
)
```

这里：

```ts
(tc) => tools?.find((t) => t.name === tc.name)
```

`=>` 是箭头函数；`find` 返回的是匹配的整个 ToolDefinition，而不是 `true`。

如果不存在：

```text
ToolCall: delete_universe
        ↓
tools.find(...)
        ↓
undefined
        ↓
Tool not found
        ↓
根本不 execute
```

这是第一道防线：模型不能凭空获得不存在的能力。

# 4. 参数：先尽量修，再严格验证

## 4.1 prepareArguments

例如 Schema 要：

```ts
paths: string[]
```

但模型给：

```ts
paths: '["src", "tests"]'
```

可以先修成：

```ts
paths: ["src", "tests"]
```

理解：

> prepareArguments = “模型写歪了一点，能不能救回来？”

## 4.2 validateToolArguments

随后才严格检查：

```ts
Type.Object({
  pattern: Type.String(),
  paths: Type.Array(Type.String()),
})
```

如果模型给：

```ts
pattern: 123
```

就应该直接失败，根本不进入 `execute()`。

理解：

> prepare = 容错；validate = API Contract。

# 5. beforeToolCall：参数合法，不代表允许执行

例如：

```ts
pi.on("tool_call", async (event) => {
  if (
    event.toolName === "bash" &&
    String(event.input.command).includes("rm -rf")
  ) {
    return {
      block: true,
      reason: "危险命令被阻止"
    }
  }
})
```

这层回答的是：

```text
Schema：这个调用是否合法？
beforeToolCall：这个调用允不允许？
```

所以 `bash({command: "rm -rf ..."})` 从类型上完全可以合法，但产品策略仍然可以阻止。

# 6. executePreparedToolCall：一个工具真正怎么跑

核心教学版：

```ts
async function executePreparedToolCall(prepared, signal, emit) {
  const updateEvents: Promise<void>[] = []
  let acceptingUpdates = true

  try {
    const result = await prepared.tool.execute(
      prepared.toolCall.id,
      prepared.args,
      signal,
      (partialResult) => {
        if (!acceptingUpdates) return

        updateEvents.push(
          Promise.resolve(
            emit({
              type: "tool_execution_update",
              toolCallId: prepared.toolCall.id,
              partialResult,
            })
          )
        )
      },
    )

    acceptingUpdates = false
    await Promise.all(updateEvents)

    return { result, isError: false }
  } catch (error) {
    acceptingUpdates = false
    await Promise.all(updateEvents)

    return {
      result: createErrorToolResult(
        error instanceof Error
          ? error.message
          : String(error)
      ),
      isError: true,
    }
  } finally {
    acceptingUpdates = false
  }
}
```

### `prepared` 是什么

它可以理解成：

```ts
{
  toolCall, // LLM 原始调用
  tool,     // 找到的真正 ToolDefinition
  args,     // 修正并验证后的参数
}
```

也就是：

> “已经通过 preflight，可以执行的 ToolCall 包”。

# 7. updateEvents 不是工具并行队列

```ts
const updateEvents: Promise<void>[] = []
```

这里存的是“已经开始传播、但可能还没有完成的 UI 进度事件 Promise”，不是不同工具的执行 Promise。

例如 bash 输出三次：

```text
Installing...
Downloading...
Done.
```

工具内部调用：

```ts
onUpdate("Installing...")
onUpdate("Downloading...")
onUpdate("Done.")
```

则：

```text
updateEvents = [
  Promise(emit Installing),
  Promise(emit Downloading),
  Promise(emit Done)
]
```

### 关键：emit 是当场调用的

```ts
updateEvents.push(
  Promise.resolve(
    emit(event)
  )
)
```

执行顺序：

```text
① emit(event)
② 得到返回值
③ Promise.resolve(...)
④ push 到 updateEvents
```

所以不是“先存着，最后才发”。

`Promise.all(updateEvents)` 的作用只是 flush / barrier：

```text
update A ────────┐
update B ────┐   │
update C ──────┐ │
               │ │
         Promise.all
               ↓
       所有 update 已传播完
               ↓
       才允许最终 end/result
```

两道竞态保护：

```ts
if (!acceptingUpdates) return
```

防止工具已经 settle 后还有迟到 callback。

```ts
await Promise.all(updateEvents)
```

保证此前合法发出的 update 全部排空，再宣布最终结果。

记忆：

> close → flush → final。

# 8. Tool 自己应该把错误写清楚

Agent Runtime 外层 catch 会把异常转成：

```text
JavaScript Exception
        ↓
AgentToolResult
+ isError: true
        ↓
ToolResultMessage
        ↓
下一轮 LLM
```

例如文件不存在：

```text
fs.readFile
   ↓
ENOENT
   ↓
tool.execute reject
   ↓
executePreparedToolCall catch
   ↓
Error ToolResult
```

所以工具作者应该尽量提供可恢复错误：

```ts
throw new Error(
  `文件不存在：${params.path}，请先检查目录或使用 ls/find 查找实际路径`
)
```

而不是：

```ts
throw new Error("失败")
```

因为 Tool error 不是只给程序员看的日志，也是 Agent 的反馈信号。

好的错误应该帮助 Agent知道：

```text
发生了什么
为什么失败
哪个输入导致
下一步怎么恢复
```

# 9. afterToolCall：最终结果进入 Context 前还有一道门

例如可以做：

```text
密钥脱敏
结果截断
增加 metadata
修正 isError
```

例子：

```ts
pi.on("tool_result", async (event) => {
  return {
    content: event.content.map((block) => {
      if (block.type !== "text") return block

      return {
        ...block,
        text: block.text.replace(
          /sk-[A-Za-z0-9_-]+/g,
          "[REDACTED_API_KEY]"
        )
      }
    })
  }
})
```

所以：

```text
Tool 原始结果
    ↓
afterToolCall / tool_result hook
    ↓
安全、脱敏、截断后的结果
    ↓
ToolResultMessage
    ↓
LLM Context
```

# 10. Extension、pi、factory 三个对象终于分清

这是今天第二个最大的理解点。

## Extension

真正存储注册结果的“盒子”：

```ts
const extension = {
  tools: new Map(),
  handlers: new Map(),
  commands: new Map(),
  shortcuts: new Map(),
}
```

理解：

> Extension = 注册表 / 插件容器。

## pi / ExtensionAPI

Host 提供给插件的一组受控 API：

```ts
pi.registerTool(...)
pi.on(...)
pi.registerCommand(...)
```

理解：

> pi = 操作 Extension 的接口，不是存储本身。

## factory

扩展 TS/JS 默认导出的初始化函数：

```ts
export default function (pi) {
  pi.registerTool(...)
  pi.on(...)
}
```

理解：

> factory = 插件初始化函数；拿着 Host 给的 pi，把自己的能力注册进去。

# 11. Extension Loader：外面的 TS 为什么不用手写 import

流程：

```text
搜索扩展路径
    ↓
发现 .ts / .js
    ↓
jiti / dynamic import
    ↓
拿到 default export factory
    ↓
创建空 Extension
    ↓
创建 ExtensionAPI（pi）
    ↓
await factory(pi)
    ↓
执行 pi.registerTool / pi.on
    ↓
函数引用进入 Extension 的 Map
    ↓
commit
```

最核心一行：

```ts
await factory(load.api)
```

直接读成：

> “执行插件初始化函数，并把 Pi 的插件 API 传给它。”

它不是把所有 `export function` 自动注册，也不是 factory 返回一个新的 pi。

例如：

```ts
export function helperA() {}
export function helperB() {}

export default function (pi) {
  pi.registerTool({
    name: "hello",
    execute: helperA,
  })
}
```

Pi 不会自动注册 `helperA/helperB`；只有 default factory 明确调用注册 API 的内容才进入 Extension。

# 12. 函数为什么离开 TS 文件后还能调用：保存的是函数引用

JavaScript / TypeScript 中函数是一等对象：

```ts
function hello(name) {
  console.log(name)
}

const x = hello
x("Tom")
```

所以注册：

```ts
pi.on("tool_call", handler)
```

本质是：

```ts
extension.handlers
  .get("tool_call")
  .push(handler)
```

保存的是 `handler` 的函数引用。

以后运行时不需要重新打开 TS 文件：

```ts
const handlers = extension.handlers.get("tool_call")

for (const handler of handlers) {
  await handler(event, ctx)
}
```

同理：

```ts
pi.registerTool({
  name: "hello",
  execute: helloExecute,
})
```

保存的是：

```text
ToolDefinition
└── execute → helloExecute Function
```

运行时直接：

```ts
await tool.execute(...)
```

# 13. 闭包：为什么注册函数还能记住外面的变量

例如：

```ts
export default function (pi) {
  const protectedPaths = [".env", ".git/"]

  pi.on("tool_call", async (event) => {
    if (
      protectedPaths.some(
        p => event.input.path?.includes(p)
      )
    ) {
      return { block: true }
    }
  })
}
```

factory 早就执行结束了，但 handler 仍然能访问 `protectedPaths`。

因为 handler 闭包捕获了它创建时的词法环境。

同样，ToolDefinition 的包装 execute：

```ts
execute: (toolCallId, params, signal, onUpdate) =>
  definition.execute(
    toolCallId,
    params,
    signal,
    onUpdate,
    ctxFactory?.(),
  )
```

这个包装函数闭包捕获：

```text
definition
ctxFactory
```

因此 Agent Core 只需要统一四参数 execute，coding-agent 产品层可以动态补第五个 ExtensionContext。

# 14. Operations：不是 execute 时临时换，而是创建 Tool 时注入

例如 Read Tool 不直接硬编码：

```ts
fs.readFile(path)
```

而依赖接口：

```ts
interface ReadOperations {
  readFile(path: string): Promise<Buffer>
  access(path: string): Promise<void>
}
```

默认：

```ts
const readTool = createReadTool(cwd)
```

内部使用：

```text
defaultReadOperations
        ↓
Node fs
        ↓
本机文件
```

也可以创建时注入：

```ts
const readTool = createReadTool(cwd, {
  operations: sshReadOperations,
})
```

于是相同 execute 代码：

```ts
await ops.readFile(path)
```

实际变成读远程 SSH 文件系统。

所以：

> execute 写业务算法；Operations 决定底层 I/O 去哪执行。具体实现通常在创建 Tool 时注入，然后被 execute 闭包捕获。

这是 Dependency Injection + Strategy + Closure。

# 15. `pi.on()` 与 `session.subscribe()`：原理类似，路由和等待语义不同

共同本质：

```text
保存函数引用
    ↓
未来事件发生
    ↓
Host 调函数并把 event 传进去
```

## `pi.on(type, handler)`

注册时就指定类型：

```ts
pi.on("tool_call", handler)
```

存储：

```text
handlers
├── tool_call  → [A, B]
└── tool_result → [C]
```

事件发生：

```ts
const handlers = extension.handlers.get(event.type)

for (const handler of handlers) {
  await handler(event, ctx)
}
```

它是：

> 按类型路由的 Hook Registry。

而且 `tool_call` / `tool_result` 等 Extension Hook 通常是需要等待的，因为它们可能参与权限、修改结果等控制路径。

## `AgentSession.subscribe(listener)`

注册：

```ts
session.subscribe(listener)
```

存储通常是一个扁平 listeners 数组：

```text
[
  tuiListener,
  rpcListener,
  loggerListener,
]
```

发送事件：

```ts
for (const listener of listeners) {
  listener(event)
}
```

所有 listener 都收到，由自己判断：

```ts
if (event.type === "tool_execution_end") {
  ...
}
```

它是：

> 广播型 Event Stream。

### 注意第三种：`Agent.subscribe()`

不要和 `AgentSession.subscribe()` 混淆。

记忆：

```text
Agent.subscribe()
→ listeners 会被 await

AgentSession.subscribe()
→ 更偏广播通知，不作为控制 barrier

pi.on()
→ ExtensionRunner 按事件类型路由，控制型 hook 通常 await
```

# 16. event 参数到底怎么传进 listener

没有编译器魔法。

最小实现：

```ts
class Session {
  listeners = []

  subscribe(listener) {
    this.listeners.push(listener)
  }

  emit(event) {
    for (const listener of this.listeners) {
      listener(event)
    }
  }
}
```

外部：

```ts
function myListener(event) {
  console.log(event)
}

session.subscribe(myListener)
```

注册阶段只是：

```text
listeners.push(myListener 函数引用)
```

以后：

```ts
session.emit({
  type: "tool_execution_end",
  toolName: "bash",
})
```

Host 实际执行：

```ts
myListener({
  type: "tool_execution_end",
  toolName: "bash",
})
```

所以整个 callback / subscribe / on / hook 系统最底层只有两件事：

```text
① 保存函数引用
② 未来某个时刻调用函数，并传参数
```

# 17. Tool update 如何一路实时传到 TUI

完整链路：

```text
Tool
 │
 │ onUpdate(partialResult)
 ▼
executePreparedToolCall
 │
 │ emit(tool_execution_update)
 ▼
Agent Event
 │
 ▼
AgentSession._handleAgentEvent
 │
 ├── ExtensionRunner
 │
 └── session._emit(event)
        │
        ▼
InteractiveMode listener
        │
        ▼
pendingTools.get(toolCallId)
        │
        ▼
ToolExecutionComponent.updateResult()
        │
        ▼
ui.requestRender()
        │
        ▼
TUI render
        │
        ▼
Terminal
```

`toolCallId` 很重要，因为多个工具可以同时有 update：

```text
call_A → BashComponent
call_B → GrepComponent
call_C → ReadComponent
```

收到某个 `tool_execution_update` 后，用 ID 精确找到对应 UI Component 更新。

这和 Codex 的 Item ID / item delta 思想非常接近。

# 18. Coding Agent 的消息为什么比模型消息“胖”很多

例如：

```ts
{
  role: "bashExecution",
  command: "npm test",
  output: "...",
  exitCode: 1,
  cancelled: false,
  truncated: true,
  fullOutputPath: "/tmp/full.log",
  timestamp: 123456,
  excludeFromContext: false,
}
```

这些字段不是纯给 LLM 的，而是产品运行时的完整事实。

可以分：

```text
command / output / exitCode / cancelled
→ LLM + UI + Session 都可能需要

truncated / fullOutputPath
→ 告诉模型和 UI：当前 output 只是摘要，完整 artifact 在哪里

timestamp
→ 更偏 Session / persistence / 排序

excludeFromContext
→ Session 可以保留，但 LLM Context 可以排除
```

所以：

```text
Coding Agent AgentMessage
= 产品世界的完整领域事实

pi-ai Message
= 给模型看的最小语义投影
```

# 19. `convertToLlm()` 不是简单删字段，而是语义投影

例如：

```ts
{
  role: "bashExecution",
  command: "npm test",
  output: "FAIL ...",
  exitCode: 1,
  truncated: true,
  fullOutputPath: "/tmp/full.log",
  timestamp: 123456,
}
```

可能转成模型理解的：

```text
Ran `npm test`

FAIL ...

Command exited with code 1

[Output truncated. Full output: /tmp/full.log]
```

注意：

```text
timestamp 字段可能完全消失
```

但：

```text
truncated: true
```

虽然结构字段消失，它的语义被转成自然语言提示。

所以：

> convert 不是“删字段”，而是“保留模型需要的语义，改变表示形式”。

这也是为什么：

```text
Session History ≠ LLM Context
```

最佳原则：

> 存储尽量保留结构；给模型时再做 projection。

# 21. `agent_end`：Loop 结束，不等于对象销毁

```ts
{
  type: "agent_end",
  messages: [...]
}
```

含义：

> 这一次 Agent run 的低层 loop 不会再继续产生下一 Turn，但这个“最后事件”仍然需要向上层广播并完成收尾。

所以不是：

```text
agent_end
→ 对象销毁
→ 谁都收不到
```

而是：

```text
runLoop 决定结束
    ↓
emit(agent_end)
    ↓
listeners 收到最后事件
    ↓
UI / telemetry / session 做收尾
    ↓
run 真正进入 idle / settled
```

要区分：

```text
agent_end
= 低层 Agent run 结束

agent_settled
= 更高层 session run 也已经稳定，没有 retry / continuation 等后续动作
```

```text
        ↓
模型只看到需要的语义投影
```

# 23. 一句话复习

- `Extension`：真正存 Tool / handler / command 的插件容器。
- `pi`：Host 给插件的受控注册 API。
- `factory`：扩展默认导出的初始化函数，执行 `factory(pi)` 完成注册。
- `registerTool`：把 ToolDefinition / execute 函数引用写入注册表。
- `pi.on`：按事件类型保存 handler，ExtensionRunner 负责路由调用。
- `subscribe`：保存 listener，事件发生时 Host 主动执行 `listener(event)`。
- `Operations`：Tool 创建时注入的底层 I/O 策略，execute 只调用接口。
- `prepareArguments`：容错；`validate`：契约；`before`：权限/策略；`after`：结果治理。
- `catch`：把 Exception 变成 Agent 可理解、可恢复的数据。
- `updateEvents`：正在传播的进度事件 Promise，不是工具并行队列。
- `Promise.all(updateEvents)`：flush barrier，保证 update 先于 final。
- `BashExecutionMessage`：产品领域消息，不是 LLM 原生 Message。
- `convertToLlm`：语义投影，不是简单 stringify / 删字段。
- `agent_end`：本次 loop 的最后通知，不代表 Agent 对象立刻销毁。
